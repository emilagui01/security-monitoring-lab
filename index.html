Catching cyberattacks in a practice network

I built a small company network on my laptop, turned on the security records that a security team relies on, then safely acted out seven things real attackers do. For each one I found the evidence in the records, explained what it showed, and cleaned up, the same way an IT security analyst would.

The short version

  • A server platform called Proxmox, running inside my laptop, that hosts the practice network.
  • A company account server and an employee computer, connected like a real office.
  • Security settings that record sign-ins, account changes, programs starting, and hidden commands.
  • Seven safe attack tests: password guessing, a secret admin account, a virus test file, trying to turn off antivirus, a disguised command, a program set to run on its own, and erasing the records.
  • All seven were caught. I also wrote a script that pulls every alert into one timeline.

In plain English: Building the practice network. I installed Proxmox inside my laptop, gave it a private network and two-step sign-in, then built the company account server and an employee computer and joined them together. I saved restore points along the way so any test could be undone in seconds.

1. Proxmox inside Hyper-V

Installing Proxmox directly on the laptop would have wiped Windows, so it runs as a Hyper-V VM with nested virtualization turned on. I checked the ISO's SHA256 hash against the Proxmox site before using it.

(Get-FileHash C:\ISO\proxmox-ve_9.2-1.iso -Algorithm SHA256).Hash -eq '4e88fe41...ef2c6c'   # True

New-VM -Name PVE -Generation 1 -MemoryStartupBytes 16GB -NewVHDPath "C:\HyperV\PVE.vhdx" -NewVHDSizeBytes 200GB -SwitchName "LabSwitch"
Set-VM -VMName PVE -ProcessorCount 4 -StaticMemory -AutomaticCheckpointsEnabled $false
Set-VMProcessor -VMName PVE -ExposeVirtualizationExtensions $true   # nested virtualization
Set-VMDvdDrive -VMName PVE -Path "C:\ISO\proxmox-ve.iso"

Proxmox was installed with the text installer (the graphical one can't drive Hyper-V's display), then checked from inside: /dev/kvm present and 8 vmx CPU flags, so it can run its own VMs. I switched to the free No-Subscription update repository and fully upgraded.

2. Private lab network and MFA

Windows only allows one NAT network, and my earlier labs already use it. So PVE plugs into the existing LabSwitch, and Proxmox creates its own private bridge with NAT for the new VMs:

# /etc/network/interfaces (added at the bottom)
auto vmbr1
iface vmbr1 inet static
        address 10.10.10.1/24
        bridge-ports none
        bridge-stp off
        bridge-fd 0
        post-up   echo 1 > /proc/sys/net/ipv4/ip_forward
        post-up   iptables -t nat -A POSTROUTING -s '10.10.10.0/24' -o vmbr0 -j MASQUERADE
        post-down iptables -t nat -D POSTROUTING -s '10.10.10.0/24' -o vmbr0 -j MASQUERADE

The web console's root login now requires a TOTP code from an authenticator app (something you know plus something you have), with single-use recovery keys stored in a password manager.

Account lockout

Set-ADDefaultDomainPasswordPolicy -Identity seclab.local -LockoutThreshold 5 `
  -LockoutDuration 00:15:00 -LockoutObservationWindow 00:15:00

Lockout rules live in the Default Domain Policy because password and lockout settings only work at the domain level.

Troubleshooting: audit policy saved but never applied

CheckResultWhat it told me
gpresult /rAppliedThe GPO reached both machines
Script block logging registry key1The registry part of the GPO worked
auditpol /get /category:*No AuditingThe audit part did not apply. The DC even lost its defaults, because "force subcategory" was on with nothing to replace them
audit.csv in SYSVOLAll 11 settingsThe settings were saved correctly
gPCMachineExtensionNamesMissing F3CCC681Root cause: the Audit Policy Configuration client-side extension wasn't registered on the GPO, so Windows never ran the code that reads audit.csv

Fix: toggling one audit setting off and back on in the GPO editor re-registered the extension {F3CCC681-B74C-4060-9F26-CD84525DCA2A}. After gpupdate /force, both machines showed the expected Success and Failure auditing. A GPO can hold correct settings and still not apply them, so I narrowed it down one layer at a time: applied, then effective, then stored, then registered.

#1

Password guessing and lockout

Nov 20, 5:44:22 to 5:44:54 PM · logged on SEC-DC01
SimulateEntered a wrong password for SECLAB\tstark six times at the SEC-WIN11 sign-in screen until Windows reported the account locked out.
DetectDomain logons are checked on the DC, so the evidence is in SEC-DC01's Security log, not the client's.
EventTimeKey fields
4771 ×85:44:22 to 5:44:54Kerberos pre-auth failed for tstark, Client Address ::ffff:10.10.10.30, Failure Code 0x18 (bad password)
47405:44:52Account locked out: tstark, Caller Computer Name: SEC-WIN11

Eight 4771s for six attempts: Windows can send two Kerberos requests for one attempt, and the last one came after the lockout. Older 4771s for SEC-WIN11$ were the computer account reconnecting, normal background noise.

RespondThe same fix as a real locked-out user ticket:
Search-ADAccount -LockedOut | Select-Object Name, SamAccountName
Unlock-ADAccount tstark
WhyFive failures on one account is a forgotten password. Failures across many accounts from one computer is password spraying. 4740's Caller Computer Name tells them apart.
#2

Backdoor Domain Admin account

Nov 20, 6:03:41 to 6:04:49 PM · SEC-DC01
SimulateAn attacker with access creates a boring-sounding account and makes it a Domain Admin:
New-ADUser -Name "backup_svc" -SamAccountName backup_svc -AccountPassword (Read-Host -AsSecureString "Password") -Enabled $true
Add-ADGroupMember "Domain Admins" backup_svc
EventTimeKey fields
47206:03:41User account created: backup_svc, by SECLAB\Administrator
47286:04:49Member CN=backup_svc added to Domain Admins, TargetSid ending in -512
RespondRemoved and disabled the account, then confirmed only Administrator remained:
Remove-ADGroupMember "Domain Admins" backup_svc -Confirm:$false
Disable-ADAccount backup_svc
Get-ADGroupMember "Domain Admins" | Select-Object Name     # Administrator
WhyEvery domain uses RID 512 for Domain Admins, so an alert on any 4728 whose TargetSid ends in -512 catches this even if the group is renamed.
#3

Malware download (EICAR test file)

Nov 20, 6:19 to 6:26 PM · SEC-WIN11 as tstark
SimulateDownloaded the EICAR test files from eicar.org. EICAR is a harmless text string every antivirus is built to flag, so detection can be tested without real malware.
DetectTwo layers caught it:
LayerTimeWhat happened
Edge SmartScreen6:19 PMBlocked eicar_com.zip before it was saved
1116 / 11176:20 PMA first detection and block while the test page was open
11166:23:06Virus:DOS/EICAR_Test_File, Severe, C:\Users\tstark\Downloads\eicar.txt, Real-Time Protection
11176:26:41Action: Quarantine. Process: Notepad.exe, the program that tried to write the file

Viewing the .txt in the browser didn't trigger a popup, because nothing was saved to disk. Saving the same string from Notepad did: "Operation did not complete successfully because the file contains a virus."

#4

Turning off Defender

Nov 20, 6:54 to 7:08 PM · SEC-WIN11
SimulateDisabling security tools is one of the first things ransomware does. From an admin PowerShell:

#5

Encoded PowerShell command

Nov 20, 7:19:47 PM · SEC-WIN11 as tstark
SimulateAttackers Base64-encode commands so a quick look at the logs shows nothing readable. This one only prints text:
$c = [Convert]::ToBase64String([Text.Encoding]::Unicode.GetBytes('Write-Output "lab test"'))
powershell -EncodedCommand $c
EventTimeWhat it shows
46887:19:47powershell.exe -EncodedCommand plus unreadable text, started by another powershell.exe, Medium integrity (normal user)
41047:19:49Script block logging recorded the decoded command: Write-Output "lab test", user SECLAB\tstark

4688 says something suspicious ran. 4104 says what it actually did. PowerShell also marked some 4104 events as Warning on its own when it saw suspicious code, a free second flag. Reading the Security log needed an admin Event Viewer: a standard user gets Access is denied, which is by design.

RespondDecoded and reviewed: benign test. In a real case, the next steps are checking the parent process and isolating the host.
#6

Persistence with a scheduled task

Nov 20, 7:42:14 to 7:46:53 PM · SEC-WIN11
SimulateAttackers create tasks so their program runs again after every sign-in, named to look harmless:

#7

Nov 21, 7:25:47 PM · SEC-WIN11

In plain English: Instead of searching one record at a time, I made a saved view that shows every alert together, and a script that exports all of them into one spreadsheet. Then I ran two quick searches that pick the attacks out of thousands of normal events.

Custom view: Security Lab Alerts

One Event Viewer view across the Security, Defender and PowerShell logs, filtered to 4625, 4688, 4698, 4699, 4720, 4728, 4740, 1116, 1117, 5001, 5013, 4104, 1102: 1,794 events, newest first.

security-hunt.ps1

security-hunt.ps1 asks Windows for only the matching events with -FilterHashtable (much faster than reading whole logs) and writes one sorted timeline.

# security-hunt.ps1 - pull lab alert events from the last 2 days into one CSV
$since = (Get-Date).AddDays(-2)
$queries = @(
  @{LogName='Security'; Id=4625,4688,4698,4699,1102},
  @{LogName='Microsoft-Windows-Windows Defender/Operational'; Id=1116,1117,5001,5013},
  @{LogName='Microsoft-Windows-PowerShell/Operational'; Id=4104}
)
$events = foreach ($q in $queries) {
  $q.StartTime = $since
  Get-WinEvent -FilterHashtable $q -ErrorAction SilentlyContinue
}
$events | Sort-Object TimeCreated |
  Select-Object TimeCreated, LogName, Id, @{n='Summary';e={($_.Message -split "`r?`n")[0].Trim()}} |
  Export-Csv C:\Users\Public\security-hunt.csv -NoTypeInformation
"Exported $($events.Count) events to C:\Users\Public\security-hunt.csv"

Result: 1,462 events. Filtered to the attack IDs, the table lines up scenarios 3, 4 and 6 in order and surfaced something I hadn't looked for: two 5013 "Tamper Protection Reverted a change" events when Tamper Protection came back on. It doesn't only block changes, it undoes them.

"...has been created.
"

First version of the CSV

SymptomEvery Summary ended with a stray quote on its own line.
CauseEvent messages end lines with CR+LF. Splitting on LF alone left a carriage return in each summary.
FixSplit on `r?`n and .Trim() the result. Every row is now one line.

Targeted searches

# only PowerShell launched with an encoded command
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4688} |
  Where-Object { $_.Message -match 'EncodedCommand' } | Select-Object TimeCreated -First 5

# every scheduled task created, by name
Get-WinEvent -FilterHashtable @{LogName='Security'; Id=4698} | ForEach-Object {
  ([xml]$_.ToXml()).Event.EventData.Data | Where-Object Name -eq 'TaskName' | Select-Object -ExpandProperty '#text' }

The first found exactly one hit, 7:19:47 PM, scenario 5, out of more than 13,000 Security events. The second listed \Updater among Windows' own \Microsoft\Windows\GroupPolicy\{...} tasks. It stands out because it isn't in a Microsoft folder. Telling routine noise apart from the real thing is most of the job.

Lessons learned

Notes
In plain English: The most useful things I took away from this project.
  • Know where the evidence lives. Domain logon failures are on the DC, not the computer the user typed on.
  • Pairs of events tell the story. 4688 plus 4104, 4720 plus 4728, 5013 next to 5001: one says something happened, the other says what.
  • Defaults aren't enough. Process creation, command lines and script blocks are off until you turn them on.
  • Verify the setting, not just the policy. gpresult said the GPO applied; auditpol showed it hadn't.
  • Protection has layers. SmartScreen, real-time scanning and Tamper Protection each stopped something the others didn't.
  • Save evidence first. Exporting the log before clearing it kept every event from the lab.
  • Snapshots make it safe to break things. Every risky step had a restore point.
